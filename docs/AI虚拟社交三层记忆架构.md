# AI虚拟社交三层记忆架构：让 AI 记住一段关系

用户和一个 AI 角色聊了三个月。今天他说：

> 我最近又睡不好了，可能还是因为换工作的事。

这句话里混着三种完全不同的记忆：

- “这轮对话里刚说了什么”，需要立刻接上。
- “最近一段时间都在焦虑工作和睡眠”，需要保留阶段连续性。
- “用户不喜欢被催睡觉”“用户正在评估换工作机会”，可能会长期影响后续互动。

如果只靠最近几轮上下文，三天前聊过的状态很快会丢。如果把所有东西都写进长期记忆，短期情绪、阶段状态和稳定事实又会混在一起，后面召回时很难判断哪条该信、哪条该过期。

三层记忆要解决的就是这个问题：短期原文、阶段摘要、长期事实分开存，召回时再融合。

## 先看结论

**一句话：三层架构值得保留，强一致治理要分阶段。**

做 AI 虚拟社交，记忆系统很容易走向两个极端。

一种是只把最近几轮对话塞进上下文，长期互动很快失去连续感。另一种是一开始就堆满强一致、补偿和治理链路，首版还没上线，就已经变成一套沉重的事务平台。

更稳妥的做法是：先把 `L1 / L2 / L3` 的职责拆清楚，跑通写入、召回、删除、重建四条主链路；再把删除防复活、历史重建强一致、记忆衰减、人工治理这些长期能力放到后面按风险启用。

整套能力按三档推进：

| 分级 | 目标 | 适用判断 |
| --- | --- | --- |
| 首版主链路 | 让三层记忆真实可用 | 优先完成 |
| 稳定性增强 | 降低重复、脏摘要、部分失败影响 | 体验稳定后推进 |
| 强一致治理 | 面向规模化、合规删除、历史修复 | 有明确风险后启用 |

请优先记住 6 条原则：

1. `L1` 是当前会话的短期上下文缓存，不是可信来源，也不承担跨会话连续性。
2. `L2` 是阶段摘要，不替代长期事实。
3. `L3` 是长期原子记忆，需要按 `user_id × character_id` 强隔离。
4. 首版也必须有记忆域安全底线：敏感内容拦截、用户可删、删除审计和基础留存策略不能后置到“以后再说”。
5. 首版默认支持有边界的降级召回：普通闲聊单层失败时可返回其他可用记忆；删除确认、敏感查询、隔离异常这类场景必须失败关闭。
6. 写入栅栏、删除墓碑、语义抑制、衰减、死信任务这些增强治理能力，不适合反过来卡住首版主路径。

先记住一个读法：`user_id × character_id` 是业务隔离口径，不是某个 Mem0 版本的固定 API 签名。具体怎么落到 Mem0，由 adapter 负责。

下面先补三个阅读前置：Mem0 在架构里的位置、首版必须守住的安全底线，以及首版主路径总览。后面的正文再展开三层分工和四条主链路。

### 先补一个概念：Mem0 是什么

后文会频繁提到 Mem0。先把它的位置讲清楚：在这套三层架构里，Mem0 不是 L1 的短期上下文窗口，也不是 L2 的阶段摘要生成器，而是 L3 这层“长期记忆后端”。

应用把一组 `user -> assistant` 对话交给 Mem0。Mem0 负责从里面提取值得长期保留的事实、偏好或事件，并提供分类、去重、语义检索、过滤、数量限制、阈值和重排等长期记忆能力。后续应用用自然语言问题去查，Mem0 再返回相关长期记忆。

举个例子：用户在对话里说“别总提醒我早点睡，我会有压力”。这句话不应该只留在最近几轮上下文里，也不应该由业务代码手写正则抽取成偏好。更合适的做法是把完整轮次交给 Mem0，让它沉淀出类似“用户不喜欢被催促睡觉”的长期偏好；下次角色想关心睡眠时，再通过 L3 检索把这条偏好召回，避免踩同一个雷。

所以，业务层不要再手写一套“抽取事实、去重、向量化、入库、语义检索”的引擎。业务层真正要管的是产品边界：这条记忆属于哪个用户、哪个角色、哪个会话来源；它从哪轮对话来；删除、重建、审计和最终 prompt 预算怎么处理。

在本文里，Mem0 的位置可以简单理解为：

- `add`：把一组对话交给 Mem0，让它判断是否形成长期记忆。
- `search`：按查询语义和过滤条件找回相关长期记忆。
- `update/delete`：在业务明确要求修正或删除时，显式修改或清理记忆；业务层的范围删除语义由 adapter 按业务索引逐条删除实现，不直接调用 Mem0 原生 `delete_all()`。
- `filters / top_k / threshold / rerank`：优先用 Mem0 自带的检索控制能力，应用层只做最后的跨层融合和预算裁剪。

还要注意一点：Mem0 的 SDK、Platform、过滤语义和实体作用域会随版本变化。本文里的 `mem0.add`、`mem0.search` 都应该理解成业务 adapter 需要具备的能力口径，不能直接等同于某个固定版本的原生签名。范围删除是 Thinkback 的业务操作，不等同于 Mem0 原生 `delete_all()`。

### 首版先画一条底线：记忆域安全

三层记忆不是“能记多少记多少”。虚拟社交里的睡眠、情绪、工作、人际关系、亲密度和偏好，都可能带有隐私或敏感属性。首版不能把安全、删除和留存全部推到强治理阶段。

首版至少要先做到四件事：

- 记忆域准入：系统提示词、内部控制指令、工具回显、密钥凭证、越权诱导和平台明确禁止沉淀的内容，不进入任何一层长期或阶段记忆。
- 用户可控：用户要求删除某条记忆、某个会话来源或该角色下全部记忆时，系统有明确入口、任务状态和结果反馈。
- 删除审计：记录谁在什么作用域发起删除、删除了哪些业务索引、是否触发 L2 重建；审计记录不保存被删正文。
- 基础留存：至少为敏感类别、事件类记忆和关系状态预留 `data_classification / expires_at` 或等价字段，分级口径见 4.3，避免首版上线后完全无法治理。

这条底线和后面说的强一致治理不是一回事。首版可以不上写入栅栏、删除墓碑和语义抑制，但安全准入、用户删除和审计记录要先具备。

安全准入还有一个容易漏掉的细节：被硬规则拒绝的材料，不只是“不调用 Mem0 add”。它也不能进入 L2 摘要，不能作为 L1 的记忆注入材料进入 prompt，后续重建时也不能从可靠轮次存储里再次回流。工程上可以把这类原始轮次保留在上游对话域或受限审计材料里，但它们不应成为记忆域输入。

## 1. 设计目标

> 先回答一个问题：为什么不是只用短期上下文，或者只用向量库长期记忆。

三层记忆架构要解决三个问题：

- 当前短期记忆窗口内要有即时上下文（低延迟、可裁剪）
- 近期多轮、跨会话的信息要能压缩成阶段性摘要（低成本、可滚动更新、可跨会话延续）
- 跨阶段、跨会话要能保留稳定长期记忆条目（由 Mem0 等记忆后端判定是否沉淀、可更新删除、可语义检索）

一句话总结：

- L1 解决“刚刚聊到哪里”。
- L2 解决“最近这段关系和状态是什么”。
- L3 解决“长期应该记住什么”。

这三类问题混在一起，系统会变得既不准，也不好删；分开之后，后面的写入、召回、删除和重建才有清晰边界。

## 2. 三层记忆如何分工

> 先把分工讲清楚，再讨论流程和工程边界。

三层记忆最容易被误解成“同一份内容存三遍”。更准确的理解是：同一轮对话会被加工成三种不同粒度的上下文材料，分别服务即时上下文、阶段连续性和长期事实检索。理解这一点，后面的流程图与接口规约才不会显得复杂。

### 2.1 一句话架构

> 结论：三层不是重复存三份记忆，而是从同一轮对话里提取三种不同粒度的上下文材料。

记忆域以 `user_id × character_id` 作为业务强隔离作用域，把每个完整对话轮次送入三类不同用途的记忆材料处理。

`L1` 保存当前会话最近若干完整轮次，默认可从 10 轮起步，并叠加上下文预算裁剪。`L2` 把阶段性互动压缩成一份滚动摘要。`L3` 通过 Mem0 判断是否沉淀为可语义检索、可显式更新和可删除的长期原子记忆。

重建能力不只来自 Mem0，还依赖可靠轮次存储、历史对话源和业务索引。三层不是复制同一份内容，而是从同一份完整轮次输入中提取不同粒度的上下文材料。

虚拟社交里可以这样理解：用户刚说“我今晚又失眠了”时，`L1` 保留当前会话的原文细节；连续几天都在聊工作压力时，`L2` 把“最近处在职业焦虑和睡眠波动中”压成阶段摘要；用户明确说“我不喜欢被人催睡觉”或“我养了一只猫”时，`L3` 才沉淀成以后仍可能反复用到的长期记忆。三层不是为了显得复杂，而是避免把短期情绪、阶段状态和长期事实混在同一个桶里。

这类 `短期窗口 + 阶段摘要 + 长期记忆` 的拆分符合常见记忆系统的基本取向：近期上下文和长期记忆分开处理。AI 虚拟社交额外需要 `L2`，因为用户与角色会长期互动，关系温度、近期计划和待跟进事项不一定适合沉淀成长期事实，却很适合用摘要持续带入后续回复。

### 2.2 三层职责

> 阅读提示：实现时要避免三层互相代替：L1 不承担可信来源，L2 不承担长期事实，L3 不承担阶段叙事压缩。

#### L1：短期上下文

L1 是当前会话的短期窗口。它保存当前会话最近若干完整轮次，默认可以从 10 轮起步，再叠加上下文预算裁剪。

它只回答“刚刚聊到哪里”。它不是事实库，也不承担跨会话连续性。L1 丢了，体验会短暂变差，但不能影响 L2/L3 的可信输入来源。

#### L2：阶段摘要

L2 是用户与角色之间的阶段摘要。它压缩近期互动主线、关系温度、当前困扰、计划和待跟进事项。这里的“阶段”不建议无限滚动成一份越来越厚的画像，首版可以按最近 N 轮、最近一段自然时间，或“当前关系阶段”配置窗口；窗口之外仍有长期价值的内容交给 L3。

例如“用户最近处在职业焦虑和睡眠波动中”，更适合放在 L2，而不是长期事实库。它描述的是一段时间里的状态，不一定是永久事实。

首版口径要明确区分 `dirty` 和 `stale`。`dirty` 表示摘要可能包含已删除或已纠正的事实，召回必须跳过，直到重建修复；`stale` 表示摘要没有包含最新轮次，但旧内容本身未被污染，可以带着“落后”标记降级注入，也可以由策略选择跳过。两者不宜混成同一种状态。

#### L3：长期原子记忆

L3 是长期原子记忆，优先交给 Mem0 管理。写入侧优先复用 Mem0 的抽取、分类和去重能力；检索侧优先复用 Mem0 的语义检索、过滤、数量限制、阈值和重排（rerank）能力；显式更新和删除由业务命令通过 adapter 调用 Mem0 update/delete 完成。范围删除按业务索引列出当前 `user_id × character_id` 下的 backend memory id 后逐条 delete，不能直接调用 Mem0 原生 `delete_all()`。遇到“用户明确纠正旧事实”这类冲突时，不假设一次 `add` 一定能自动处理干净，而是通过 Mem0 能力加业务侧显式 update/delete/rebuild 收敛。

业务侧可以在元数据里补充 `memory_type`，但这只是展示、审计或产品枚举，不应把画像、偏好、事件、关系这类枚举做成替代 Mem0 分类能力的自研记忆引擎。

三层边界可以压缩成一张表：

| 层级 | 解决的问题 | 不应该承担 |
| --- | --- | --- |
| L1 短期上下文 | 当前会话最近原文 | 跨会话连续性、长期事实来源 |
| L2 阶段摘要 | 近期状态、关系温度、待跟进事项 | 长期事实库、原文归档 |
| L3 长期记忆 | 稳定事实、偏好、重要事件 | 阶段叙事压缩、短期窗口 |

小结：

- L1 负责“近”，L2 负责“这一段”，L3 负责“长期可检索的事实、偏好和事件”。
- L2 脏了就跳过，不做带风险的降权注入。
- L3 能交给 Mem0 的能力，不在业务层重复实现。

### 2.3 主路径如何流动

> 主路径只回答三件事：怎么写入、怎么召回、怎么避免单层失败拖垮整体体验。

先不看接口和字段，主路径可以拆成四个动作：

| 动作 | 首版要点 |
| --- | --- |
| 写入 | 从完整轮次开始，不接收孤立单条消息；`round_id` 是业务幂等锚点 |
| 存储 | 完整轮次先进入可靠轮次存储，作为 L2/L3 的可信输入来源 |
| 沉淀 | L1 是派生缓存；L2 和 L3 从同一份可靠轮次材料任务化沉淀 |
| 召回 | 先判断需要哪些层；Mem0 负责 L3 检索，业务层负责跨层融合、冲突处理和 prompt 预算 |

写入入口先做三件事：

1. 契约校验：检查 `user_id / character_id / session_id / round_id / messages[]`。
2. 规范化和安全守卫：过滤不应进入记忆域的内容。
3. 幂等登记：用 `round_id` 登记沉淀任务，再持久化完整轮次。

这里的“任务化”不等于首版必须马上引入独立 worker。首版可以同步执行 L2/L3 沉淀，但任务身份、状态、错误和结果必须可查；等流量、耗时或重试需求出现后，再把同一套任务模型迁到异步 worker。

召回策略不要在不同场景里来回摇摆。首版可以先固定成一条清晰规则：

| 场景 | 召回策略 |
| --- | --- |
| 普通闲聊、流程控制、即时改写 | 默认读取 `L1 + L2`，可跳过 L3 |
| 记忆追问、个人信息追问 | 必须查 L3 |
| 偏好相关回复、关系连续性回复 | 必须查 L3 |
| 删除确认、隐私请求、敏感信息查询 | 失败关闭，不做降级伪装 |

召回结果进入 prompt 前，还要经过业务召回融合层。这里最容易把 Mem0 和业务层混成一件事，可以拆开看：

| 处理步骤 | 谁负责 | 具体含义 |
| --- | --- | --- |
| L3 检索过滤 | Mem0 优先 | 在长期记忆内部按 filters、top_k、阈值和 rerank 找出相关记忆；`user_id × character_id` 隔离要先由业务 adapter、命名空间或组合键保证 |
| 跨层安全过滤 | 业务层 | 把不应进入 prompt 的材料剔除，例如已删除、dirty 摘要、越权来源、敏感策略不允许的内容 |
| 跨层去重 | 业务层 | L2 摘要里已经说过的事实，L3 不要再原样重复；多个 L3 返回同一含义时保留更可信的一条 |
| 冲突处理 | 业务层 | 当前用户输入优先；L3 与 L2 冲突时，本轮按 L3，并记录 L2 待修正信号 |
| Prompt 预算裁剪 | 业务层 | 按 token 预算选择进入 prompt 的内容：L1 留必要原文，L2 留阶段主线，L3 留强相关长期事实 |

检索参数优先使用 Mem0 已提供的过滤、数量限制、阈值和重排能力。只有当 Mem0 当前模式无法表达业务优先级时，应用层才做最小放大召回和最终预算裁剪。

### 2.4 删除、重建和衰减如何处理

> 关键判断：首版要先保证“删得到、摘要能修、历史能重放”。这不等于一开始就要上写入栅栏、删除墓碑和语义抑制；那些属于强治理阶段。

删除要解决两个问题：

- 目标长期记忆不能继续被召回。
- 已经吸收到 L2 摘要里的内容，也不能继续进入 prompt。

删除不是一个动作吃掉所有场景。删除范围不同，L3、L2 和当前会话缓存的处理也不同：

| 删除范围 | L3 怎么处理 | L2 怎么处理 | 当前会话缓存怎么处理 |
| --- | --- | --- | --- |
| 单条长期记忆 | 校验作用域后调用 Mem0 delete | 可能包含该事实时标记 `dirty`，触发重建 | 通常不处理；如果当前 prompt 已取到旧材料，刷新本轮召回结果 |
| 某个会话来源 | 按 `source_refs` 判断删除、显式更新或重算 | 覆盖该会话历史时标记 `dirty` | 让该 session 的 L1 缓存失效或重新加载 |
| 全部记忆 | 清空该 `user_id × character_id` 下的 L3 | 清空或重建 L2 摘要材料 | 让相关会话缓存失效，避免继续展示旧记忆 |

会话删除最容易出错。一条 L3 不一定只来自一个会话。Mem0 可能把多个会话里的相似事实合并成一条长期记忆，也可能在后续对话里强化同一事实。因此业务索引要把 `source_refs` 设计成可追踪来源集合或关联表，而不是单个字符串。

重建时先看来源，不能只看“要重建哪个范围”：

| 场景 | 可信来源 |
| --- | --- |
| 正常沉淀 | 记忆服务已接纳的可靠轮次存储 |
| 删除、修复、全量重建 | 上游历史对话源的只读回放 |
| 当前会话缓存 | 只用于当前会话体验，不支持删除和重建决策 |

按单个会话重建时，只限制 L3 的删除和重写范围；L2 是跨会话的阶段摘要，应按 L2 配置窗口，基于删除或修复后的有效历史重算。

衰减是长期治理能力：

- 只治理 L3 事件类记忆的召回优先级。
- 不删除、不归档、不影响 L1、L2 和稳定偏好。
- 未启用衰减时，首版可用更新时间、重要性和检索分数做轻量排序。
- 启用衰减后，`low` 只表示排序靠后，不表示自动淘汰。

### 2.5 Mem0 边界

> 边界原则：长期记忆不重复造轮子。Mem0 已提供的能力优先复用，业务层只补它不理解的产品边界。

L3 不应该自研“抽取 -> 拼装 -> 向量落库”这套记忆引擎。读这一节时只抓一个问题：长期记忆能力交给谁，产品边界由谁兜住。

可以按这张表拆边界：

| 能力 | 优先交给谁 | 业务层只补什么 |
| --- | --- | --- |
| 事实抽取 | Mem0 | 提供完整轮次 |
| 分类 | Mem0 | 记录 Mem0 原始分类；产品稳定消费的业务枚举见 4.3 |
| 去重 | Mem0 | 记录 `backend_memory_id` |
| 语义检索 | Mem0 | 传入 adapter 已隔离后的 filters、top_k、threshold、rerank 参数 |
| 显式删除/更新 | Mem0 + 业务命令 | 校验作用域，记录审计 |
| 隔离、来源、审计 | 业务层 | 管住 `user_id × character_id` 和 `source_refs` |

换句话说：

- Mem0 做长期记忆引擎：抽取、分类、去重、检索、过滤、重排。
- 业务层做产品边界：用户角色隔离、来源追踪、任务追踪、审计、L1/L2、最终召回融合。
- 业务层不要做第二套记忆引擎：不要自己拼向量库，不要用业务枚举替代 Mem0 分类，不要假设一次 `add` 必然能处理所有冲突。

冲突收敛也按这个原则处理：能由 Mem0 处理的交给 Mem0；不能稳定表达的部分，业务侧再用显式 update/delete/rebuild 兜底。

这里有一个容易踩坑的点：Mem0 不同 SDK / Platform 版本里的实体、过滤、命名空间和返回语义可能不同。文章里写 `mem0.add`、`mem0.search`，表达的是“业务 adapter 应该具备这类能力”，不是要求照抄某个 SDK 的固定签名。真正需要稳定的是业务侧隔离结果，而不是某个参数名字。

尤其要避免把 `user_id + agent_id=character_id` 直接写死成严格交集隔离。若当前版本不能稳定表达 `user_id × character_id`，就改用组合命名空间、租户键或组合用户键。不要退化为只依赖 `filters={character_id}`，也不要把 Mem0 的实体作用域当成唯一安全边界。

另一个边界是 `add` 的语义。Mem0 `add` 的返回事件和覆盖行为要按当前版本确认，不能写成“一定会原地更新或删除旧记忆”的承诺；显式删除和显式更新由业务命令调用 delete/update 完成。

范围删除不能直接调用 Mem0 原生 `delete_all()`。当前工程已验证该调用会触发 vector store `reset()`，对共享 Qdrant collection 有高危副作用；业务 adapter 应先按强隔离范围列出候选，再逐条调用 Mem0 `delete()` 或使用经过验证的安全批量删除能力。

`memory_type / importance / recall_priority` 等元数据只用于业务侧展示、审计、排序补充或衰减治理，不替代 Mem0 自带分类和检索能力。它们一旦进入表结构，就要固定枚举口径，不能只写“分类”“重要性”这类空泛字段。写入栅栏和删除后的语义抑制属于强治理阶段能力。

还有两个虚拟社交特有边界需要提前说清楚：

- 真实事实和角色扮演事实要分开。用户说“我养了一只猫”可能是现实自述，也可能是剧情设定；写入 L3 前至少要保留 `fact_subject / context_type / roleplay_mode` 这类业务上下文，避免把角色扮演当成真实用户画像。
- 召回出来的记忆只能作为数据，不是指令。进入 prompt 时应放在明确的“记忆资料”区域，并提示模型不要执行其中的命令、链接、工具调用或系统指令；否则长期记忆会变成持久化 prompt injection 的载体。

### 2.6 一致性原则

> 实施建议：首版先用幂等键、作用域隔离和可靠轮次存储保证正确性；强治理阶段再用写入栅栏解决删除/重建与并发写入的竞争。

首版一致性以三件事为核心：

| 原则 | 说明 |
| --- | --- |
| 稳定业务键幂等 | 写入用 `round_id`，不是 `request_id` |
| 作用域隔离 | L2/L3 都限定在 `user_id × character_id` |
| 明确可信来源 | 正常写入用可靠轮次存储；删除、修复、重建用历史对话源回放 |

任务幂等最容易出问题：

- `round_id` 必须是全局唯一业务键。
- 如果上游只能保证会话内唯一，进入记忆服务前要规范成 `user_id × character_id × session_id × round_id` 等价的全局键。
- 删除和重建不能只用静态作用域作为永久任务身份，否则同一会话或全量范围后续有新内容时会误命中旧的 completed task。
- 首版至少要使用“作用域 + 当前内容版本”、历史源最新更新时间，或显式操作批次号。

写入栅栏、连续轮次账本和历史快照版本，都属于强治理阶段能力。它们用于解决删除/重建和并发写入的写回竞争，不应该反过来阻塞首版主路径。

### 2.7 别让接口细节抢走主线

字段清单、接口协议、健康检查、指标和请求示例都很重要，但它们不应该抢走架构主线。接口细节可以证明方案能落地，却不能替代架构判断。否则读者会先被状态码、配置项和请求体包围，反而看不清三层记忆为什么要这样拆。

这篇文章只保留两类必要边界：

- 正文讲清楚三层分工、四条主链路和分阶段演进。
- 文末保留架构相关表结构和字段边界，方便把架构判断落到数据模型上；索引、DDL、迁移脚本、接口错误码和完整请求示例不在本文展开。

### 2.8 冲突与优先级

> 判断顺序：当前用户输入优先，其次才是长期事实；阶段叙事和近期上下文用于补充语境，不和长期事实竞争可信度。

先记住一个顺序：

```text
当前用户输入 > L3 长期记忆 > L2 阶段摘要 > L1 最近原文补充
```

如果用户本轮说“我现在不讨厌被提醒睡觉了”，本轮回复就要尊重当前输入，不能继续沿用旧 L3 里的“用户不喜欢被催睡觉”。

常见冲突可以这样处理：

| 冲突类型 | 本轮怎么处理 | 后续怎么修复 |
| --- | --- | --- |
| 当前输入 vs L3 | 当前输入优先 | 触发 L3 更新或重建 |
| L3 vs L2 | L3 优先 | 标记 L2 待修正 |
| 新旧 L2 摘要 | `summary_cursor_round` 更新者优先 | 淘汰落后摘要 |
| L3 内部冲突 | 用户显式更新、重要性、更新时间、明确否定优先 | 优先用 Mem0 能力收敛，不足时业务侧显式处理 |

这里要区分两件事：上面的排序是“可信度和冲突处理顺序”，不是 prompt 里的物理拼接顺序。上下文拼接可以是 `L2 -> L1 -> L3`，让模型先看到阶段主线，再看到最近原文，最后看到强相关长期事实；但一旦内容冲突，仍按 `当前用户输入 > L3 > L2 > L1` 判断本轮该信哪一版。

### 2.9 第一版、增强版、强治理版怎么分

> 最重要的实施判断：首版负责跑通主链路，稳定后再补体验，规模化后再补强一致治理。

三层记忆架构、`user_id × character_id` 隔离和核心业务链路属于首版能力；强一致、强补偿和完整审计系统按风险逐步开启。这里要区分两层审计：首版必须记录删除和重建的基础审计结果；链路追踪、审计系统联动、人工治理台属于后续增强。

这张表不是重新讲一遍结论，而是帮助落地时判断“哪些必须现在做，哪些可以等风险出现后再做”：

| 分级 | 应该先做 | 暂时不做 |
| --- | --- | --- |
| 首版主链路 | L1/L2/L3、写入幂等、融合召回、基础删除、手动重建、任务状态、`user_id × character_id` 隔离 | 写入栅栏、删除墓碑、语义抑制、衰减分片、死信人工处置 |
| 稳定性增强 | 跳过无关 L3 查询、跨层去重、预算裁剪、L2 标脏、基础重试、任务查询 | 复杂 carry-forward、语义级防复活、历史快照强一致 |
| 强一致治理 | 写入栅栏、删除墓碑、语义抑制、历史快照版本、死信处置、事件类记忆衰减 | 不反向阻塞首版主路径 |

首版必须守住下面几条规则，直接看系统行为是否符合预期：

| 规则 | 要做到什么 | 为什么 |
| --- | --- | --- |
| 隔离规则 | L2/L3 的读写必须限定在 `user_id × character_id`；L1 还要限定当前 `session_id` | 避免 A 用户、B 角色或其他会话的记忆串到当前对话里 |
| 来源规则 | 正常写入用可靠轮次存储；删除、修复、重建用上游历史对话源回放；L1 只做当前会话缓存 | L1 可能过期、被裁剪或只保存最近几轮，不能拿它恢复长期记忆 |
| 幂等规则 | 写入用 `round_id` 去重；删除和重建用 `operation_id + scope + history_version` 或等价业务键去重 | 用户重复点击、接口重试或 worker 重跑时，不能产生重复记忆或重复删除 |
| 删除规则 | 已删除的 L3 不再召回；可能包含已删事实的 L2 要标记 dirty 并重建 | 只删 Mem0 里的 L3 不够，摘要里可能还残留同一事实 |
| 降级规则 | 普通闲聊可以缺一层先答；删除确认、隐私请求、敏感查询、隔离异常、安全策略失败和协议错误必须失败关闭 | 能聊天不等于能假装记忆正常，涉及隐私和删除时必须保守 |

小结：

- 首版不追求“治理能力一次到位”，只追求主链路真实可用。
- 删除和重建必须有版本或操作批次，不能只拿静态作用域当永久任务 ID。
- 强一致能力要等真实风险出现后再开启，否则会把首版拖成事务平台。

## 3. 四条主链路

三层分工清楚之后，首版先把四条主链路跑通：写入、召回、删除、重建。

前面已经看过总览图，这里把四条主链路分别展开。每张图都刻意不画写入栅栏、删除墓碑、语义抑制和死信治理，因为这些是后续强治理能力，不应该让首版主链路变复杂。

四条流程背后的关键点只有三个：

- 写入从完整轮次进入，可靠轮次存储是正常沉淀的可信输入来源，L1 只是派生缓存。
- 召回不是把三层原样拼接，而是融合后再进入 prompt。
- 删除不只删 L3；如果 L2 摘要可能已经吸收了被删事实，就必须标脏并重建。

### 3.1 写入链路

```text
┌──────────────────────────────┐
│ 完整对话轮次进入              │
│ user -> assistant 成对提交    │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 契约与安全校验                │
│ 字段 / 作用域 / 记忆域准入    │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 幂等与轮次持久化              │
│ round_id / reliable journal   │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 登记沉淀任务                  │
│ task status / extract L2/L3   │
└──────┬───────────────────────┘
       │
       ├──────────────► L1 刷新
       │                最近轮次缓存，失败不影响可信来源
       │
       ├──────────────► L2 摘要
       │                dirty 跳过 / stale 滚动 / 阶段摘要
       │
       └──────────────► L3 长期记忆
                        硬跳过规则 / Mem0 add
                        分类 / 去重 / 语义抽取
                        记录 backend_memory_id + source_refs
```

写入从完整的 `user -> assistant` 轮次开始，不接收孤立的单条消息。入口先做契约校验、幂等校验和安全守卫，再把完整轮次落到可靠轮次存储。L1 只是派生缓存；L2 和 L3 都从这份可靠材料沉淀。首版可以同步执行沉淀逻辑，但要留下任务状态和结果；后续再把执行挪到异步 worker。

L3 写入可以再展开一层：

```text
┌──────────────────────────────┐
│ L3 写入候选轮次               │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 硬跳过规则                    │
│ 空内容 / 系统指令 / 工具回显  │
│ 密钥凭证 / 高风险注入内容     │
└───────┬──────────────────────┘
        │ 命中
        └──► skipped，不进入记忆域材料
              不进入 L2/L3，也不作为 L1 注入资料
              后续重建也不得回流
        │
        ▼ 未命中
┌──────────────────────────────┐
│ 调用 Mem0 add                 │
│ 语义抽取 / 分类 / 去重         │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 业务索引记录                  │
│ backend_memory_id             │
│ user_id × character_id        │
│ source_refs / metadata        │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 冲突兜底                      │
│ 必要时显式更新 / 删除 / 重建  │
└──────────────────────────────┘
```

首版不建议业务层自己写一套 LLM 抽取与分类引擎。业务侧只做“确定不能进入记忆域”的硬规则判断；只要不是确定性跳过，就交给 Mem0 判断是否形成长期记忆。Mem0 返回的分类、去重、记忆 ID 和事件结果，再由业务侧记录到 `tb_memory` 索引里。业务侧的 `memory_type / importance / metadata` 只作为审计、展示和排序补充，不替代 Mem0 的抽取逻辑。

这里的硬跳过要前置于 L2 和 L3：命中系统指令、工具回显、密钥凭证、高风险 prompt injection 的材料，不能进入阶段摘要，也不能在后续重建时被当作有效历史重新送入 Mem0。

首版重点：

- `round_id` 是写入幂等锚点，不是 `request_id`。
- L1 写失败只影响短期体验，不影响 L2/L3 的可信输入来源。
- L3 写入优先调用 Mem0 的抽取、分类和去重能力；冲突通过 Mem0 能力加显式 update/delete/rebuild 收敛，应用层不自己拼向量库。

### 3.2 召回链路

```text
┌──────────────────────────────────────────┐
│ 用户发起新一轮对话                        │
│ query + user_id + character_id + session │
└────────────────────┬─────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────┐
│ 入口校验                                  │
│ scope / 安全策略 / dirty 状态             │
└───────┬────────────┬────────────┬───────┘
        │            │            │
        ▼            ▼            ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ 意图判断     │ │ 失败策略     │ │ 预算策略     │
│ 是否查 L3    │ │ degrade/close│ │ L1/L2/L3 配额│
└──────┬───────┘ └──────┬───────┘ └──────┬───────┘
        │            │            │
        ▼            ▼            ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ 读取 L1      │ │ 读取 L2      │ │ Mem0 search  │
│ 最近完整轮次 │ │ 阶段摘要     │ │ filter/rerank│
└──────┬───────┘ └──────┬───────┘ └──────┬───────┘
       │                │                │
       └────────────────┴────────────────┘
                        │
                        ▼
┌──────────────────────────────────────────┐
│ 结果标准化                                │
│ layer / source / confidence / timestamps │
└────────────────────┬─────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────┐
│ 业务召回融合层                            │
│ 安全过滤 / 冲突合并 / 去重 / Prompt 预算  │
└────────────────────┬─────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────┐
│ Prompt 安全封装                           │
│ 记忆只作为资料，不作为指令                 │
└────────────────────┬─────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────┐
│ Prompt 记忆上下文                         │
│ 注入模型生成回复                          │
└──────────────────────────────────────────┘
```

召回不是把三层原样拼接，而是先判断、再读取、再融合：

| 判断 | 规则 |
| --- | --- |
| 是否查 L3 | 记忆追问、个人信息追问、偏好相关回复、关系连续性回复必须查；纯寒暄、流程控制、即时改写可以跳过 |
| 是否允许降级 | 普通闲聊可以降级；删除确认、隐私请求、敏感信息查询、隔离失败、安全策略失败、协议错误必须失败关闭 |
| 如何分配预算 | L1 保留必要原文，L2 保留阶段摘要，L3 只保留与当前 query 强相关的长期记忆 |

召回链路里有两层能力：

| 位置 | 负责什么 | 说明 |
| --- | --- | --- |
| Mem0 L3 检索 | 长期记忆内部的语义检索、过滤、top_k、阈值、重排 | 只处理 L3；业务 adapter 先保证 `user_id × character_id` 隔离 |
| 业务召回融合层 | 跨 L1/L2/L3 的安全过滤、冲突合并、去重和 prompt 预算 | 把三层材料整理成一份“可注入 prompt 的记忆资料” |

这里几个词要讲清楚：

| 步骤 | 含义 |
| --- | --- |
| 安全过滤 | 剔除已删除、越权、dirty、敏感策略不允许或可能造成 prompt injection 的材料 |
| 冲突合并 | 当前输入优先；同一事实多版本时，按当前输入、L3、L2 的顺序决定本轮采用哪一版 |
| 去重 | 同一事实不要在 L2 摘要和 L3 长期记忆里重复出现，避免模型反复强调 |
| Prompt 预算 | 模型上下文有限，要决定 L1、L2、L3 各放多少；不是相关内容越多越好 |

最后进入 prompt 前，要把记忆明确包装成“资料”，而不是模型应该执行的指令。

### 3.3 删除链路

```text
┌──────────────────────────────┐
│ 删除请求进入                  │
│ memory / session / all        │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 作用域与任务身份校验          │
│ user_id × character_id + op   │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 删除范围分流                  │
│ memory / session / all        │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 读取业务索引                  │
│ tb_memory / source_refs       │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 处理 L3                       │
│ delete / update / indexed range │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 当前会话缓存失效               │
│ 仅用于避免本轮继续使用旧材料    │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 标记或重建 L2                  │
│ dirty 跳过，修复后再召回       │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 记录任务与审计                │
│ task status / 脱敏 result     │
└──────────────────────────────┘
```

删除要解决两个问题：

- 目标记忆不能继续被召回。
- 已经污染到 L2 摘要里的内容，不能原样注入上下文。

首版先保证三件事：L3 删除或更新、L2 标脏或重建、当前会话缓存失效。当前会话缓存只做运行态刷新，用来避免本轮 prompt 继续拿到删除前已经读出的旧材料；它不是删除和重建的数据来源。会话删除时，还要按 `source_refs` 判断 L3 是直接删除、显式更新，还是等待重算。

删除范围不同，L3 的处理方式也不同：

| 删除范围 | L3 处理 | L2 处理 | 当前会话缓存 |
| --- | --- | --- | --- |
| 单条 memory | 调用 Mem0 delete，业务索引标记 `DELETED` | 可能包含该事实时标记 dirty | 通常不处理；若本轮已取到旧材料，则刷新召回 |
| session 来源 | 按 `source_refs` 判断：单来源删除，多来源显式更新或重算 | 覆盖该会话历史时标记 dirty | 让该 session 的 L1 缓存失效 |
| all | 按业务索引逐条调用 Mem0 delete，禁止直接调用 Mem0 原生 `delete_all()` | 清空或重建该 `user_id × character_id` 摘要 | 让相关会话缓存失效，并处理关系状态 |

审计记录只保存操作范围、任务状态、业务索引和处理结果，不保存被删除正文。首版可以先把脱敏结果放在任务结果里，例如 affected_memory_ids、summary_state、scope、session_id；后续再接独立审计表或 trace/audit 系统。

更强的“删除后不复活”能力，例如语义抑制（suppression）、删除墓碑（tombstone）和写入栅栏（fence），可以等真实风险出现后再启用。

### 3.4 重建链路

```text
┌──────────────────────────────┐
│ 重建请求进入                  │
│ session / all / 删除后修复    │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 生成任务身份                  │
│ scope + history_version + op  │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 读取历史对话源                │
│ 删除/修复后的有效完整轮次     │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 历史过滤与排序                │
│ active rounds / source scope  │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 并行重算 L2 / L3              │
│ L2 当前阶段窗口 / dirty 清理  │
│ L3 delete/update/add          │
│ source_refs 重建              │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 版本校验与发布                │
│ history_version / task result │
└───────────────┬──────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 发布新状态                    │
│ 清 dirty/stale，记录任务结果  │
└──────────────────────────────┘
```

重建不支持从 L1 恢复。L1 只是当前会话的短期缓存，可能已经过期、裁剪或只保留最近几轮。真正用于重建的材料必须来自上游历史对话源；正常沉淀时，则使用记忆服务已经接纳的可靠轮次存储。

重建任务至少要做四个判断：

| 判断 | 说明 |
| --- | --- |
| 历史源是否已更新 | 如果历史源还没反映删除或修复结果，不能用旧历史直接重建 |
| L2 怎么重算 | 使用当前阶段窗口，不从 L1 反推，也不生成无限全量画像 |
| L3 怎么重写 | session 重建只限制 L3 来源范围；all 重建才清理整个 `user_id × character_id` 长期记忆 |
| 何时发布 | 发布前校验 `history_version / operation_id`，避免旧任务覆盖新删除或新写入后的结果 |

按单个会话重建时，只限制 L3 的删除和重写范围。L2 是 `user_id × character_id` 的阶段摘要，应按 L2 配置窗口，基于该用户角色下删除/修复后的有效历史重算。

小结：

- 写入靠可靠轮次存储保底。
- 召回靠三层融合和降级返回保体验。
- 删除靠 L3 删除/更新 + L2 标脏防污染。
- 重建靠历史源恢复，不从 L1 反推。

### 3.5 任务状态和重试

任务先保证可追踪，再考虑自动重试，最后再考虑死信任务（dead-letter）和人工处置。公众号主文不需要展开完整状态机，只要把边界讲清楚：

| 阶段 | 首版要做到 | 后续再补 |
| --- | --- | --- |
| 可追踪 | `pending / running / completed / failed`，可按 `task_id / request_id / op_type / status` 查询，状态口径见 4.3 | 更细的锁、心跳、worker 诊断 |
| 可重试 | 派发失败和短暂下游错误可重试，确定性契约错误直接失败 | 指数退避、重试窗口、失败类型分层 |
| 可治理 | `failed` 不通过重复提交入口隐式恢复 | `dead_letter`、人工跳过、人工关闭 |

首版任务要可查、可解释、可定位；完整人工治理台不需要放进主链路。

## 4. 工程落点：记忆相关表结构

> 下面只保留与记忆架构强相关的字段边界，用来说明哪些数据需要被长期追踪，哪些只是运行态或治理态信息。

如果前面是“为什么要分三层”，这一章回答的是“真正落表时不能漏掉哪些锚点”。它不是完整 DDL，也不是要求首版一次把所有治理字段都做完。读的时候只抓三类信息：隔离字段、来源字段、治理字段。只要这三类锚点留下，后续删除、重建和审计才有地方落。

### 4.1 数据契约

这里不是完整 DDL，而是把前面的架构判断落到字段边界。首版字段宁可少，也不能缺少隔离、追踪和治理锚点。

把架构落到数据层时，最容易犯的错误是“先把能想到的字段全塞进去”。记忆系统不应该这样设计。字段的价值主要有三类：

| 字段价值 | 要回答的问题 |
| --- | --- |
| 隔离 | 这条摘要、记忆或任务属于哪个用户和哪个角色 |
| 追踪 | 它来自哪轮对话、哪个会话、哪个后端记忆 ID |
| 治理 | 它是否有效、能不能删除、是否需要重建、是否涉及留存 |

既不参与隔离，也不参与追踪和治理的字段，不应该进入首版最小模型。

先用一张总表看五类数据各自解决什么问题。这里先看锚点摘要，完整字段在后面逐表展开：

| 契约 | 首版关键锚点 | 解决的问题 |
| --- | --- | --- |
| `tb_current_summary` | 作用域、摘要正文、推进游标、摘要状态 | 当前摘要是谁的、推进到哪一轮、是否落后 |
| `tb_summary_round_journal` | 作用域、轮次幂等键、完整消息、来源时间、轮次状态 | L2/L3 正常沉淀时从哪里取完整轮次 |
| `tb_memory` | Mem0 后端 ID、业务作用域、来源集合、现实/剧情上下文、删除和留存状态 | Mem0 记忆与业务作用域、来源、删除状态怎么对齐 |
| `tb_user_character_state` | 用户角色作用域、关系摘要、状态版本、最近互动时间 | 用户和角色之间的关系状态如何单独管理 |
| `tb_memory_task` | 任务身份、操作类型、作用域、幂等键、历史版本、状态和脱敏结果 | 写入、删除、重建任务是否可查、可重试、可审计 |

字段名可以按团队规范调整，但表的职责边界不建议混用。

`messages[]` 首版推荐保存完整 `user -> assistant` 配对，但不要把物理结构锁死成永远只能两条消息。系统事件、撤回、编辑、多模态和主动消息都需要后续扩展空间。建议统一成 `message_id / role / normalized_content / timestamp` 这类可扩展结构。

强治理阶段再补齐 `write_fence_version / summary_cas_token / recall_priority / last_recalled_at / recall_count / deleted_at` 等字段。`data_classification / expires_at` 不建议完全后置，至少应在首版预留。当前工程用 `round_state=active / deleted_tombstone` 控制轮次是否参与摘要和重建；`deleted_tombstone` 在首版先作为来源排除标记使用，强治理阶段再扩展成完整删除墓碑和语义级防复活能力。

历史对话源由上游对话域负责，不属于 L1。记忆服务只通过只读 adapter 使用它；L1 仍然只是当前会话缓存。

### 4.2 五张记忆相关业务表

数据库表只保存业务索引、审计、状态和治理字段。L3 写入侧的抽取、分类和去重优先交给 Mem0；检索侧的语义检索、过滤、阈值和重排也优先交给 Mem0；显式更新和单条删除由业务命令调用 Mem0 update/delete，范围删除由业务索引逐条 delete 实现。

这五张表放在同一节里讲，是为了把边界一次讲清楚。读的时候不要先盯字段数量，而要先看每张表负责哪类问题，避免把摘要、长期记忆、关系状态和任务状态混成一张大表。

| 表 | 主要职责 | 容易混淆的点 |
| --- | --- | --- |
| `tb_current_summary` | 保存当前可用的 L2 阶段摘要 | 不是历史归档，也不是长期事实库 |
| `tb_summary_round_journal` | 保存已接纳完整轮次，作为 L2/L3 正常沉淀材料 | 不是 L1 缓存，也不是上游完整历史库 |
| `tb_memory` | 保存 Mem0 长期记忆的业务索引和治理状态 | 不是自研长期记忆存储 |
| `tb_user_character_state` | 保存用户和角色之间的关系状态 | 不是 L3 长期原子记忆 |
| `tb_memory_task` | 保存写入、删除、重建等任务状态和脱敏结果 | 不是业务记忆内容表 |

下面逐张说明首版必需字段和治理增强字段。首版可以只实现“必需字段”，治理增强字段按风险逐步补齐。

#### 4.2.1 `tb_current_summary`

`tb_current_summary` 保存某个 `user_id × character_id` 当前可用于召回的 L2 阶段摘要。它只保存“当前摘要视图”，不负责保存所有历史轮次。

首版必需字段：

| 字段 | 作用 |
| --- | --- |
| `summary_id` | 摘要 ID，用于查询和审计 |
| `user_id / character_id` | 摘要所属作用域 |
| `summary_text` | 当前阶段摘要正文 |
| `summary_cursor_round` | 摘要已经推进到的轮次游标 |
| `latest_source_round_id` | 最近纳入摘要的来源轮次 |
| `latest_source_timestamp` | 最近纳入摘要的来源时间 |
| `summary_state` | `active / stale / dirty / rebuilding`，口径见 4.3 |
| `created_at / updated_at` | 排障、排序和版本判断 |

治理增强字段：

| 字段 | 什么时候需要 |
| --- | --- |
| `summary_version` | 需要摘要版本管理或回滚 |
| `summary_cas_token` | 需要防止并发写入覆盖 |
| `rebuild_task_id` | 需要追踪摘要由哪个任务修复 |
| `summary_window / window_policy` | 需要明确摘要窗口，例如最近 N 轮、自然时间或当前关系阶段 |
| `metadata` | 记录模型版本、摘要策略、窗口配置等 |

#### 4.2.2 `tb_summary_round_journal`

`tb_summary_round_journal` 保存记忆服务已经接纳的完整轮次。正常写入时，L2 摘要和 L3 长期记忆都从这里取材料；重建时则使用上游历史对话源的只读回放。它不是 L1 缓存。

首版必需字段：

| 字段 | 作用 |
| --- | --- |
| `journal_id` | 轮次日志 ID |
| `user_id / character_id / session_id` | 用户、角色和会话作用域 |
| `round_id` | 写入幂等业务键 |
| `round_index` | 会话内顺序，便于排序和重建窗口判断 |
| `round_fingerprint` | 防重复和内容变更识别 |
| `messages` | 规范化后的完整轮次消息数组 |
| `source_timestamp` | 轮次发生时间 |
| `round_state` | 当前工程区分 `active / deleted_tombstone`，用于控制是否参与摘要和重建；`deleted_tombstone` 在首版表示来源已被排除，强治理阶段再扩展完整墓碑语义，口径见 4.3 |
| `created_at / updated_at` | 排障和重建版本判断 |

治理增强字段：

| 字段 | 什么时候需要 |
| --- | --- |
| `history_version` | 需要删除、修复和重建版本校验 |
| `schema_version` | `messages` 结构可能演进 |
| `ingest_trace_id` | 需要追踪写入链路 |
| `deleted_at` | 强治理阶段需要删除墓碑 |

`messages` 首版推荐保存完整 `user -> assistant` 配对，并统一为 `message_id / role / normalized_content / timestamp`。后续系统事件、撤回、编辑、多模态和主动消息都可以在这个结构上扩展。

#### 4.2.3 `tb_memory`

`tb_memory` 是长期记忆业务索引表。它记录 Mem0 长期记忆和业务侧边界之间的对应关系：

- 这条记忆属于哪个 `user_id × character_id`。
- Mem0 后端里的 ID 是哪个。
- 它来自哪些会话和轮次。
- 它当前是否仍然有效，是否涉及敏感分级和留存。

它不是自研向量记忆引擎，也不直接替代 Mem0 的长期记忆存储。

首版必需字段：

| 字段 | 作用 |
| --- | --- |
| `memory_id` | 业务侧记忆 ID，用于审计和查询 |
| `backend_memory_id` | Mem0 返回的记忆 ID，用于 get/update/delete 对齐 |
| `user_id / character_id` | 用户和角色的强隔离作用域 |
| `source_refs` | 追踪记忆来自哪些会话、哪些轮次；建议用关联表或数组表达多来源 |
| `source_type` | 表达业务来源；枚举口径见 4.3 |
| `fact_subject / context_type / roleplay_mode` | 区分现实自述、角色扮演和剧情设定；枚举口径见 4.3 |
| `memory_status` | 控制业务侧是否仍认为有效；枚举口径见 4.3 |
| `data_classification / expires_at` | 首版预留的敏感分类和基础留存边界；枚举口径见 4.3 |
| `memory_type / backend_categories` | 业务侧稳定分类和 Mem0 原始分类，枚举口径见 4.3 |
| `metadata` | 记录 trace_id、Mem0 配置版本、治理标记等扩展信息 |
| `created_at / updated_at` | 支撑排序、排障和重建版本判断 |

治理增强字段：

| 字段 | 什么时候需要 |
| --- | --- |
| `scope_type` | 确实存在 USER_GLOBAL / CONVERSATION 等不同生效范围；枚举口径见 4.3 |
| `importance / confidence_score` | 需要业务侧排序补充或用户确认机制；取值口径见 4.3 |
| `access_count / last_accessed_at` | 需要分析召回使用情况或做衰减治理 |

这些增强字段可以按产品需要逐步增加，但边界要守住：

- `memory_type` 不决定 Mem0 如何抽取或更新。
- `source_type` 只表达业务来源，不参与语义检索。
- `scope_type=USER_GLOBAL` 要谨慎使用，虚拟社交默认推荐 `USER_CHARACTER`。
- `memory_status=SUPPRESSED` 属于强治理阶段字段，真正是否参与 L3 召回，仍要通过 Mem0 delete/update/filter 或 adapter 层过滤共同保证。

#### 4.2.4 `tb_user_character_state`

用户-角色关系状态表，追踪每对用户与角色之间的关系演进、亲密度和情绪信号。它更接近 L2/关系状态补充，适合注入 Prompt 的关系层，不应混作 L3 长期原子记忆。

首版必需字段：

| 字段 | 作用 |
| --- | --- |
| `relationship_id` | 用户-角色关系 ID |
| `user_id / character_id` | 关系所属作用域 |
| `relationship_summary` | 当前关系状态的自然语言描述 |
| `state_version` | 乐观锁版本，避免并发覆盖 |
| `last_interaction_at` | 最近一次互动时间 |
| `created_at / updated_at` | 排障和状态更新时间 |
| `data_classification / expires_at` | 首版预留；后续按隐私、留存或删除治理规则细化，分级口径见 4.3 |

治理增强字段：

| 字段 | 什么时候需要 |
| --- | --- |
| `intimacy_score` | 产品需要稳定的亲密度数值 |
| `relationship_stage` | 产品需要明确关系阶段枚举；枚举口径见 4.3 |
| `recent_emotional_signal` | 需要把近期情绪作为独立信号使用；枚举口径见 4.3 |
| `total_interaction_count` | 需要运营统计或关系成长规则 |
| `metadata` | 记录关系里程碑、特殊标记等扩展信息 |

关系状态和三层记忆的边界：

- `relationship_summary` 可以作为 L2 阶段摘要的补充输入，但不替代 `tb_current_summary`。
- 亲密度、关系阶段、近期情绪属于角色互动状态，不应写成 Mem0 L3 长期事实，除非产品明确需要长期保留某个用户自述事实。
- 删除用户或用户-角色记忆时，该表必须纳入同一审计和级联治理范围。

#### 4.2.5 `tb_memory_task`

`tb_memory_task` 保存记忆写入、删除、重建等任务的状态。它不保存记忆正文，只保存任务身份、作用域、状态、错误摘要和脱敏结果，方便重试、排障和审计。首版可以同步执行任务，但任务记录不能省略。

首版必需字段：

| 字段 | 作用 |
| --- | --- |
| `task_id` | 任务 ID |
| `request_id` | 请求追踪 ID，不作为业务幂等主键 |
| `op_type` | `write_round / delete_memory / delete_session / delete_all / rebuild_l2 / rebuild_l3`，口径见 4.3 |
| `scope` | 任务作用域，例如 `user_id × character_id`、session 或 memory |
| `operation_id` | 删除、重建等用户操作的业务幂等键 |
| `history_version` | 重建或删除修复时使用的历史版本 |
| `status` | `pending / running / completed / failed`，口径见 4.3 |
| `retry_count` | 已重试次数 |
| `last_error` | 最近一次错误摘要，不保存敏感正文 |
| `result` | 任务脱敏结果，例如影响的业务索引、summary_state、是否跳过，不保存被删正文 |
| `created_at / updated_at` | 排障和状态更新时间 |

治理增强字段：

| 字段 | 什么时候需要 |
| --- | --- |
| `locked_by / locked_until` | 需要多 worker 并发消费 |
| `started_at / finished_at` | 需要统计任务耗时 |
| `next_retry_at` | 需要指数退避或延迟重试 |
| `dead_letter_reason` | 需要人工处置失败任务 |
| `trace_id / audit_id` | 需要打通链路追踪和审计系统 |

任务表最容易犯的错误，是把 `request_id` 当成业务幂等键。写入幂等看 `round_id`，删除和重建幂等看 `operation_id + scope + history_version` 或等价业务键。

五张表放在一起看，边界会更清楚：`tb_summary_round_journal` 承接写入材料，`tb_current_summary` 服务 L2 召回，`tb_memory` 对齐 Mem0 L3，`tb_user_character_state` 保存关系状态，`tb_memory_task` 追踪任务。它们可以关联，但不应该互相替代。

### 4.3 分类与枚举口径

只要字段会被存储、过滤、排序、审计或展示，就不要只写“分类”“状态”“重要性”。首版可以先少，但口径要清楚。

下面是一套适合 AI 虚拟社交的起步枚举。具体产品可以调整命名，但同一个系统里必须保持统一。

为了避免这一节变成枚举字典，可以按三组阅读。先看分组，再看具体取值：

| 分组 | 首版是否建议明确 | 作用 |
| --- | --- | --- |
| 记忆内容和来源 | 建议首版明确 | 决定这条记忆是什么、从哪里来、属于现实还是剧情 |
| 治理和召回控制 | 建议至少预留 | 决定能不能召回、是否敏感、如何排序和删除 |
| 任务、摘要和关系状态 | 按产品复杂度启用 | 决定任务、L2 摘要和关系状态如何治理 |

先区分两个概念：

- `backend_categories`：Mem0 返回的原始分类或事件标签，建议原样记录，方便排障和版本对齐。
- `memory_type`：业务侧稳定消费的产品枚举，用于展示、审计、召回融合和治理，不替代 Mem0 的抽取、分类和去重。

`memory_type` 推荐从这几类开始：

| 值 | 含义 | 典型例子 | 使用边界 |
| --- | --- | --- | --- |
| `profile` | 相对稳定的用户画像事实 | 姓名、城市、职业、家庭角色 | 敏感信息仍要受 `data_classification` 约束 |
| `preference` | 用户偏好或互动偏好 | 喜欢的称呼、讨厌被催促、偏好的回复风格 | 当前输入明确纠正时必须更新 |
| `event` | 已发生或有时间边界的事件 | 最近面试、旅行、纪念日、争吵 | 适合做衰减排序，不适合永久高权重 |
| `plan` | 未来计划、承诺或待跟进事项 | 明天复盘、周末看展、下次继续聊某事 | 到期后应降权或转成历史事件 |
| `relationship` | 用户与角色之间的长期关系事实或里程碑 | 用户把角色视为倾诉对象、双方有固定约定 | 关系阶段本身优先放 `tb_user_character_state` |
| `constraint` | 用户明确提出的边界、禁忌或安全偏好 | 不要提某个话题、不要使用某种称呼 | 召回优先级通常高于普通偏好 |

上面这组解决“记忆是什么”。接下来解决“记忆从哪里来”。

来源类字段用于回答“这条记忆从哪里来”，不能写成一个自由文本：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `source_type` | `chat_round` | 正常对话轮次沉淀出来的记忆 |
| `source_type` | `session_rebuild` | 删除、修复或迁移后，从有效历史重建出来的记忆 |
| `source_type` | `manual_fix` | 运营、客服或用户确认后的显式修正 |
| `source_type` | `import` | 从外部系统或历史数据导入 |
| `source_type` | `system_migration` | 系统升级、模型切换或后端迁移产生 |
| `source_refs` | `session_id / round_id / message_id / source_timestamp / checksum` | 建议用集合或关联表保存，支持一条 L3 来自多个轮次 |

来源说清楚之后，还要说明这条事实属于现实用户、AI 角色，还是剧情世界。虚拟社交场景里，这个边界比普通助手更重要。

主体和场景字段用于避免把角色扮演写成真实用户画像：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `fact_subject` | `user` | 现实用户本人相关事实 |
| `fact_subject` | `character` | AI 角色设定、角色偏好或角色经历 |
| `fact_subject` | `relationship` | 用户与该角色之间的关系事实 |
| `fact_subject` | `story_world` | 剧情世界观、虚构地点、虚构组织 |
| `fact_subject` | `third_party` | 用户提到的第三方人物或外部对象 |
| `context_type` | `real_user` | 明确是现实自述 |
| `context_type` | `roleplay` | 明确处于角色扮演对话 |
| `context_type` | `fictional_setting` | 明确是剧情设定或世界观材料 |
| `context_type` | `mixed` | 现实和剧情混合，写入前最好保留证据 |
| `context_type` | `uncertain` | 无法判断现实还是剧情；首版应谨慎写入或降低置信度 |
| `roleplay_mode` | `off` | 非角色扮演 |
| `roleplay_mode` | `on` | 明确角色扮演中 |
| `roleplay_mode` | `mixed` | 现实对话和扮演交替 |
| `roleplay_mode` | `unknown` | 上游未提供可靠判断 |

接下来是治理字段。它们不一定都在首版完整启用，但最好先在模型里预留口径，避免后续删除、审计和留存没有抓手。

状态和敏感分级要直接影响召回、删除和审计：

| 字段 | 值 | 含义 | 召回处理 |
| --- | --- | --- | --- |
| `memory_status` | `ACTIVE` | 当前有效 | 可以参与召回 |
| `memory_status` | `DELETED` | 已被用户、系统或治理流程删除 | 必须跳过 |
| `memory_status` | `SUPPRESSED` | 强治理阶段的语义抑制或防复活状态 | 默认跳过，只保留治理证据 |
| `data_classification` | `normal` | 普通非敏感内容 | 按常规预算召回 |
| `data_classification` | `personal` | 可识别用户或个人生活的信息 | 需要作用域隔离和删除能力 |
| `data_classification` | `sensitive` | 健康、财务、身份、亲密关系等敏感内容 | 默认更严格过滤和更短留存 |
| `data_classification` | `restricted` | 凭证、违法风险、未成年人高风险内容等不应进入普通记忆的内容 | 默认不写入或写入治理隔离区 |

作用域、重要性和置信度要用于排序和治理，不要把它们写成“看起来有用”的装饰字段：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `scope_type` | `USER_CHARACTER` | 默认值，只在某个用户和某个角色之间生效 |
| `scope_type` | `USER_GLOBAL` | 用户全局事实，跨角色可用；虚拟社交里要谨慎开启 |
| `scope_type` | `CONVERSATION` | 只在某个会话内生效，通常更接近 L1/L2 |
| `scope_type` | `CHARACTER_GLOBAL` | 角色全局设定，不应混入用户个人记忆 |
| `importance` | `low / medium / high / critical` | 业务侧排序补充；`critical` 只给用户明确边界、安全和隐私类约束 |
| `confidence_score` | `0.0 ~ 1.0` | 抽取或分类置信度，不是真实性保证；低置信度不应写成硬事实 |
| `recall_priority` | `low / normal / high / must_use` | 强治理阶段的召回优先级；`must_use` 只适合安全边界和用户明确约束 |

最后是运行态字段。它们服务任务排障、摘要修复和关系状态，不直接替代 L3 长期记忆。

任务和摘要状态也要固定口径，否则删除、重建和重试会说不清：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `status` | `pending` | 任务已登记，尚未被 worker 接手 |
| `status` | `running` | 任务执行中 |
| `status` | `completed` | 任务成功完成，结果已记录 |
| `status` | `failed` | 任务失败，可根据失败类型决定是否重试 |
| `status` | `dead_letter` | 多次失败或需要人工处理，强治理阶段再上；首版可只预留枚举口径 |
| `op_type` | `write_round` | 完整轮次写入和任务化沉淀 |
| `op_type` | `delete_memory` | 删除单条长期记忆 |
| `op_type` | `delete_session` | 删除某个会话来源的记忆 |
| `op_type` | `delete_all` | 删除某个用户角色作用域下全部记忆 |
| `op_type` | `rebuild_l2 / rebuild_l3` | 摘要或长期记忆重建 |
| `summary_state` | `active` | 摘要可召回 |
| `summary_state` | `stale` | 摘要未覆盖最新轮次，但旧内容未污染 |
| `summary_state` | `dirty` | 摘要可能包含已删除或已纠正事实，必须跳过 |
| `summary_state` | `rebuilding` | 摘要正在修复，召回应按降级策略处理 |
| `round_state` | `active` | 轮次仍可作为摘要和重建输入 |
| `round_state` | `deleted_tombstone` | 首版用于硬跳过、删除或修复后的来源过滤，不进入摘要正文；强治理阶段再扩展为完整删除墓碑，用于防复活和历史连续推进 |

关系状态字段属于产品语义，建议单独放在 `tb_user_character_state`，不要混成 L3 原子记忆：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `relationship_stage` | `new` | 初识或关系尚未稳定 |
| `relationship_stage` | `familiar` | 已有稳定互动习惯 |
| `relationship_stage` | `trusted` | 用户愿意持续倾诉或托付上下文 |
| `relationship_stage` | `close` | 关系表达更亲近，但仍只是产品状态 |
| `relationship_stage` | `strained` | 最近出现冲突、疏离或负面反馈 |
| `relationship_stage` | `paused` | 长时间未互动或用户主动暂停 |
| `recent_emotional_signal` | `positive / neutral / anxious / sad / angry / stressed / mixed / unknown` | 只表达近期互动信号，不给用户贴长期标签 |

这些枚举不是为了让字段变多，而是为了让删除、召回、重建和审计能说清楚：哪些记忆能进入 prompt，哪些只能留作治理证据，哪些需要降权，哪些必须被跳过。

## 5. 首版验收清单

首版不要用“功能多不多”来验收，而要看几条关键路径是否可靠：

| 验收项 | 通过标准 | 不通过会怎样 |
| --- | --- | --- |
| L1 只是缓存 | L1 过期或丢失时，L2/L3 仍能从可靠轮次或历史源生成 | 最近几轮缓存一丢，长期记忆和摘要也跟着断 |
| L2 状态清楚 | `dirty` 摘要不进 prompt；`stale` 摘要可以降级或跳过 | 已删除事实可能继续通过摘要影响回复 |
| L3 交给长期记忆后端 | 抽取、分类、去重、语义检索优先使用 Mem0 或等价后端 | 业务层会重复造一套不稳定的向量记忆引擎 |
| 隔离边界明确 | L2/L3 按 `user_id × character_id` 隔离，L1 额外按 `session_id` 隔离 | 用户、角色或会话之间可能串记忆 |
| 表职责不混用 | `tb_summary_round_journal / tb_current_summary / tb_memory / tb_user_character_state / tb_memory_task` 分别承担写入材料、L2 摘要、L3 索引、关系状态和任务追踪 | 摘要、长期记忆、关系状态和任务状态混在一起，删除和重建会失去边界 |
| 删除路径完整 | 单条记忆、会话来源、全部记忆都有入口、任务状态、审计记录和 L2 修复路径 | 用户以为删了，系统后续仍可能提起 |
| 重建来源正确 | 重建只使用历史对话源或可靠轮次存储，不从 L1 反推 | 用短期缓存重建会丢历史、漏删除、制造错误摘要 |
| 召回职责清楚 | Mem0 负责 L3 检索；业务层负责跨层融合、冲突处理和 prompt 预算 | L1/L2/L3 可能被机械拼接，导致重复、冲突或超预算 |
| Prompt 安全清楚 | 召回记忆只作为“资料”进入 prompt，不作为系统指令执行 | 长期记忆可能变成持久化 prompt injection |
| 现实和扮演分开 | 用户真实事实、角色扮演事实、剧情设定有明确字段区分 | 剧情设定会污染真实用户画像 |

最后回到产品体验：用户希望 AI 记住的是一段关系，而不是一堆无法解释、无法删除的历史碎片。三层记忆的价值就在于把材料分清楚：L1 保留当前会话原文，L2 保留阶段主线，L3 保留长期事实、偏好和重要事件。这样系统既能延续关系，也能在用户要求删除或系统需要修复时，知道该改 L3、该修 L2，不能拿 L1 当恢复依据。
